# HARNESS_DESIGN.md — структурное принуждение на уровне вызова модели

## Статус

Проектная записка. Не является Foundation-документом; описывает
инструментальный слой вокруг исполнителя, а не самую методологию.

## Проблема, которую решает harness

CANON.md инструктирует модель: прочитать канон, определить этап,
выполнить Process Check, сослаться на `Foundation @ commit <hash>`.
Ничто не мешает модели это проигнорировать, забыть в длинном диалоге,
или выполнить формально и неверно. Текст не может это исправить —
это может исправить только код, который стоит между пользователем и
ответом модели.

## Принцип

Harness не пытается сделать модель более послушной. Он делает так, что
**неструктурированный или неполный ответ физически не доходит до
пользователя/репозитория** — независимо от того, что происходило
"внутри" модели.

## Минимальная схема (v0)

```
Пользователь → Harness → [1] инъекция контекста → Модель
                       ← [2] структурированный ответ ←
              [3] валидация
              [4] либо пропуск, либо отказ с диагностикой
```

### [1] Инъекция контекста (нельзя забыть прочитать файл)

Harness сам подставляет актуальное содержимое `CANON.md`,
`governance/PROJECT_STATUS.md` и текущий commit hash `main` в system/
developer-часть запроса перед каждым вызовом модели. Модель не полагается
на собственную память диалога о том, что было "прочитано ранее" —
контекст свежий при каждом вызове.

Технически: перед вызовом API — `git fetch && git rev-parse origin/main`,
чтение файлов из этого коммита, подстановка в промпт.

### [2] Требование структурированного вывода

Вместо свободного текста модель обязана вернуть JSON (или явно
размеченный блок) с полями:

```json
{
  "commit_hash_referenced": "a1b2c3d",
  "current_stage": "GS-00B review",
  "process_check": {
    "stage_goal": "...",
    "action_in_scope": true,
    "classification_if_out_of_scope": null
  },
  "answer": "..."
}
```

Это не гарантирует, что модель рассуждала правильно, но гарантирует,
что *заявленное* заключение проверяемо — можно сверить
`commit_hash_referenced` с реальным hash, механически.

### [3] Валидация (код, не модель)

Harness проверяет:
- `commit_hash_referenced` совпадает с hash, который был подставлен в [1]
  (модель не "придумала" ссылку на несуществующее состояние);
- `process_check.stage_goal` не пустой;
- если `action_in_scope: false` — `answer` обязана содержать перенаправление
  в Ideas/Backlog, а не содержательное решение вне рамок этапа.

### [4] Отказ

Если валидация не прошла — harness **не показывает ответ модели
пользователю как финальный**, а либо повторяет запрос с указанием на
конкретное нарушение, либо возвращает пользователю явную ошибку
("модель не выполнила Process Check корректно"). Это тот самый физический
барьер: плохой ответ не может тихо проскочить дальше по цепочке.

## Что harness сознательно не решает

- Не проверяет содержательную правильность рассуждения модели —
  только структурную полноту и согласованность с фактами репозитория.
- Не защищает от модели, которая просто хорошо подделывает нужный формат
  ответа, не выполнив реальной проверки. Это открытый предел любого
  подобного механизма, а не недостаток именно этой схемы.
- Не заменяет CI (`governance_lint.py`) — CI проверяет то, что реально
  попало в репозиторий; harness проверяет то, что модель заявила перед тем,
  как это попало в репозиторий. Оба слоя нужны одновременно.

## Следующий шаг реализации

v0 можно собрать как обёртку над Anthropic API (~50-100 строк): fetch
commit → сборка system prompt → вызов с response формата JSON (можно через
tool use / structured output) → валидация полей → либо публикация
результата, либо retry. Это отдельная небольшая кодовая база, не Foundation
markdown-документ — и именно поэтому её стоит держать вне канона, ссылая
на неё, а не встраивая её код в governance/.
